# 续火花完整排查记录（2026-10-30，抖音 36.8.0）

> 这份文档记录从「日志全绿但没人收到」到「10 个好友全部送达」的完整过程。
> 下次遇到类似问题（换版本、换机型、换账号）可以直接照着排查。

## 一、最终结论（先看这段）

**发送失败的唯一原因是发送链路用错了：** 只给 builder 塞了会话 ID 字符串，
抖音 IM 收下请求但不投递，消息永远卡在 `status=1（发送中）`。

**跟发送频率无关。** 修好链路后间隔 10~20 秒连发 5 个，全部成功。

## 二、正确链路（36.8.0 实测）

```java
// 1. 会话对象（不能只用字符串 ID）
ConversationListModel.Companion.inst.getConversation(conversationId)
    → com.bytedance.im.core.model.Conversation

// 2. 内容：TextContent + GsonUtil（不能手写 JSON）
TextContent content = new TextContent();
content.setText(text);
String json = GsonUtil.INSTANCE.toJson(content);
// 实际产物：{"type":0,"instruction_type":0,"item_type_local":-1,"text":"..."}

// 3. 构造消息
Message.Builder builder = client.getBeanCreateService().createMessageBuilder();
builder.conversation(conv);      // 传对象，不是字符串
builder.msgType(7);              // 文本消息
builder.content(json);
Message msg = builder.build();

// 4. 发送：IMessageUtils.sendMessage(msg, Map, IRequestListener)
IMessageUtils utils = X.12pl.LIZ();          // ★ 36.8.0 的工厂在混淆类 X.12pl
utils.sendMessage(msg, new HashMap<>(), listener);   // 回调 15 秒超时
```

### 关键类位置（36.8.0）

| 用途 | 类/方法 | 所在 dex |
|---|---|---|
| 会话列表模型 | `com.bytedance.ies.im.core.api.client.ConversationListModel` | — |
| IMessageUtils 工厂 | `X.12pl.LIZ()` | classes35 |
| 发送工具 | `com.bytedance.im.core.internal.utils.IMessageUtils.sendMessage(Message, Map, IRequestListener)` | classes35 |
| 发送回调 | `com.bytedance.im.core.client.callback.IRequestListener`（onSuccess(Object) / onFailure(IMError)） | classes23 |
| 文本内容 | `com.ss.android.ugc.aweme.im.sdk.chat.model.TextContent` | classes47 |
| 序列化 | `com.bytedance.ies.im.core.api.utils.GsonUtil` | classes35 |

**注意**：开源项目 SparkFlame / doumcp 用的是
`com.bytedance.ies.im.core.sdk.MultiInstanceHelperKt` 取 IMessageUtils，
但 **36.8.0 里这个类只剩 `LIZ()`→IConversationListModel 和 `LIZIZ()`→IConversationModelMultiInstanceExt**，
工厂被挪到了 `X.12pl`。照抄别的版本会一直「取不到 IMessageUtils」。

### 怎么自己查（换版本时必做）

```bash
# 1. 找哪个 dex 定义了类
for f in alldex/classes*.dex; do
  dexdump "$f" 2>/dev/null | grep -q "Class descriptor.*Lcom/bytedance/im/core/internal/utils/IMessageUtils;" && echo "$f"
done

# 2. 找谁返回 IMessageUtils（看 invoke-static 的调用点）
dexdump -d classes35.dex | grep -A2 "invoke-static.*IMessageUtils"

# 3. 看方法签名对不对
dexdump -d classes35.dex | awk '/IMessageUtils;/{f=1} f&&/name|type/{print}' | head
```

## 三、错误链路（v11~v18 用的）

```java
builder.conversationId("0:1:111188513589:xxxx");   // ❌ 只有字符串
builder.content("{\"text\":\"...\",\"type\":700}"); // ❌ 手写 JSON
center.sendMessage(msg, extra);                     // ❌ 无回调
// 然后每 3 秒轮询 msg.getMsgStatus() —— 这个调用本身会卡死
```

症状：
- `getMsgStatus()` 返回 1 且长期不变（发送中）
- 偶尔前 1~3 条能成功（会话对象刚好在内存里）
- 日志按「提交成功」计数，于是出现「日志全绿、没人收到」

## 四、排错时间线（怎么一步步定位的）

| 时间 | 现象 | 判断 |
|---|---|---|
| 10-30 00:56 | 9 条日志全绿，只有前 3 个人收到 | 误判为「发太快被限流」 |
| 09:51 | 加长间隔到 90~180 秒，仍然卡 status=1 | 排除频率因素 |
| 11:26 | 加 diag 上报，看到「取不到 IMessageUtils」 | 定位到工具类入口 |
| 11:54 | 改用 MultiInstanceHelperKt | 仍然取不到（36.8.0 没有这个方法） |
| 12:58 | 反查 dex 改用 `X.12pl.LIZ()` | **回调成功** |
| 13:34 | 5 个目标间隔 10~20 秒连发 | **5/5 全成功** |

## 五、配置项（云端，改完下次启动生效）

`https://www.ccios.de/spark/?token=<TOKEN>` → 对应 `~/spark-config/config.json`

```json
{
  "enabled": true,
  "targetIds": ["0:1:...", "..."],   // 会话 ID，来自 ids.json（昵称→ID）
  "messages": ["[续火花吧]"],
  "gapSeconds": [10, 20],            // 实测 10~20 秒安全
  "force": false,                    // true = 绕过「今天已跑过」门禁，已发的仍跳过（v21+）
  "forceAll": false                  // true = 连已发记录一起清空，全部重发（v21+）
}
```

**注意**：`force` 在 v20 及以前是「绕过门禁 + 清空已发」，会把已收到的人重复发一遍；
v21 起拆成 `force`（只补缺失）和 `forceAll`（全部重发）。

## 七、已知坑

1. **会话 ID 采集不全**：模块只枚举「已加载」的会话。人不在 `ids.json` 里时，让对方发一条消息 / 自己点开聊天再重开抖音。
2. **采集用的是昵称不是备注**：`ids.json` 里存的是对方昵称，跟你的备注名对不上是正常的。
3. **进程会被杀**：整轮发送要持续几分钟，抖音在后台容易被 Android 回收。**发送期间把抖音留在前台**。
4. **`/sdcard/Download` 写不进**：Android 13+ 无权限，状态文件必须放 `getExternalFilesDir()`。
5. **重复启动有锁**：日志里「已有实例在跑，退出」是正常的，防止并发重复发送。
